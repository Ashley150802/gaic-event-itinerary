ADR-001: Runtime-Agnostic Store Interface

Accepted

Context

Surket must run on three distinct hosts: local Node.js, Vercel serverless functions, and Cloudflare Workers. Each has a different storage primitive. Writing separate business logic for each host would triple the maintenance surface.

Decision

Define a single Store interface in server/src/types.ts with ~30 methods. Implement it twice: sqliteStore.ts (Node) and d1Store.ts (Cloudflare D1). All business logic depends only on the interface.

Consequences

  • Positive: Adding a new storage backend requires implementing one file. No changes to routes or analytics.
  • Positive: Verification harness tests the real code path against node:sqlite — catches regressions without mocking.
  • Negative: Both drivers must maintain SQL parity. D1-specific features used only for optimization, never correctness.

ADR-002: Node's Built-in SQLite (Zero Native Modules)

Accepted

Context

Traditional SQLite libraries (better-sqlite3, sqlite3) require C/C++ compilation, Python, and platform-specific build tools. Node.js 22.5+ ships node:sqlite as a built-in module.

Decision

Use Node's built-in node:sqlite exclusively. The dev and start scripts pass --experimental-sqlite for Node 22.5–23.3 compatibility.

Consequences

  • Positive: pnpm install never compiles anything. Zero C/C++ toolchain dependency.
  • Positive: Works on Windows without Visual Studio Build Tools or Python.
  • Negative: Requires Node 22.5+ minimum. The --experimental-sqlite flag is required for 22.5–23.3.

ADR-003: Live Tally Transport Strategy

Accepted

Context

The live tally feature requires streaming updates. Three hosts have different WebSocket capabilities: Node (long-lived), Cloudflare (Durable Objects), Vercel (ephemeral, no persistent connections).

Decision

Implement a transport-agnostic live tally with automatic fallback. GET /api/config tells the client which transport to use. Node uses in-process LiveHub, Cloudflare uses Durable Objects, Vercel falls back to 3-second polling with version-based re-rendering.

Consequences

  • Positive: Live tally works on every supported host. WebSocket failure degrades to polling gracefully.
  • Negative: Polling adds 3-second latency on Vercel. The version field must be maintained atomically.

ADR-004: Pure Analytics Engine (Zero I/O)

Accepted

Context

Analytics must be fast (live tally re-renders on every submission), consistent across runtimes, and testable. Traditional approaches embed aggregation in SQL or couple it to the ORM.

Decision

Implement aggregate.ts as a pure function with zero I/O: computeResults(survey, rows, meta) → SurveyResults. No database calls, no framework imports, fully deterministic. service.ts is the only composition point.

Consequences

  • Positive: Trivially unit-testable. Identical across all runtimes. Easy to extend with new metrics.
  • Negative: Full recomputation on every call. Acceptable because event surveys rarely exceed a few hundred responses.

ADR-005: Dark/Light Mode via CSS Custom Properties

Accepted

Context

Event operators use Surket in varied lighting conditions. The UI must support dark, light, and system modes, persist across sessions, and work with 5 accent themes — all with zero backend writes.

Decision

Use CSS custom properties with data-color-mode attribute on <html>. Dark variables on :root, light on [data-color-mode="light"]. System detection via matchMedia with change listener. Persistence via localStorage.

Consequences

  • Positive: Zero JavaScript at render time. No flash-of-wrong-theme. Works identically on all hosts.
  • Negative: Light mode required tuning every accent theme for contrast on white backgrounds.
